### 目標契約｜daily-retain-radius（凍結）
- Cross 原話：`做換店舊候選不檢查距離那件`（2026-11-13）。原文（`.handoff/LATEST.md` 第 2 段「未開始」）：`單站換店時其他自動站保留的舊候選不檢查半徑（retentionOk 沒有距離檢查）。`
- 目標：單站換店時，其他自動站保留下來的店，跟新派的店一樣都在搜尋半徑內；太遠的舊店會被換掉。
- 成功指標（白話）：換一站之後，行程裡不會留著離出發點（或地區中心）很遠的舊店。
- STOP 條件：
  1. 單站換店（帶 `shuffle`）時，其他自動站的舊候選若離 `areaPref??center` 超過 `SEARCH_BIAS_M`（3500 m）→ 不保留，該站重新搜尋，派半徑內的店（池裡沒有半徑內的店就標無候選 `empty`）。
  2. 舊候選在半徑內 → 照舊保留，不重新搜尋（Places 次數不變）。
  3. 指定、固定、已完成站不套半徑（使用者自己的選擇），照舊保留。
  4. 開地區偏好時，既有的 1 km 地區檢查照舊；不放寬。
  5. 完整重新生成（不帶 `shuffle`）行為不變。
  6. 新測試在修正前失敗、修正後通過；全套單元測試、lint、`npm run typecheck`、CI 都綠。
  7. 用真的 API 跑通一次：預覽站真 POST 單站換店，請求裡其他站帶一家遠店 → 回應換成半徑內的店；帶近店 → 保留。合併後正式站同樣驗收。證據存檔。
  8. Places 費用：只有「舊店太遠」那一站多一次搜尋（本來就該換）；其他情況不增加。
- 等級：M。理由：錯了會留著遠店（實際損失）。把關：獨立 Opus 子代理，載入 checker skill。
- 預算：預估 ~100k token，上限 ~150k。
- 保留事項：無。合併 main 已授權（2026-11-13 原話 `merge不用再我批准` `一律核准`）。
- ⚠️ 假設：
  - 半徑沿用 `SEARCH_BIAS_M` 3500 m，中心 `areaPref??center`，跟第一次挑店（`nearOk`）、換店（`usable`）同一規則。
  - 被換掉的遠店不加入排除清單；重新搜尋若又回到它，第一次挑店的半徑規則會擋掉。
