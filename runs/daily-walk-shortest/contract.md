### 目標契約｜daily-walk-shortest（凍結）
- Cross 原話（逐字，AskUserQuestion 回答，2026-11-13）：`只做步行 距離我會自己判定`
- P0 原文（`STATE.md:42` 仍未做部分）：`仍未做：總步行最短化、大眾運輸選擇。` 大眾運輸由 Cross 決定不做。
- 目標：今日行程在「固定行程晚到站數最少」的排法中，選總步行分鐘最短的那一種。
- 成功指標（白話）：Cross 照系統排的順序走，不會多走冤枉路；也不會因此比之前更容易遲到。
- STOP 條件：
  1. 晚到站數不變差：`scheduleRoute` 回報的晚到站數＝窮舉所有排法的最小晚到站數（沿用 daily-fixed-ontime STOP 3b）。
  2. 步行最短：在晚到站數最小的排法中，回傳排法的 `travelMinutes`＝窮舉最小值。隨機比對窮舉（含違反三角不等式的矩陣、已過時間的行程），不一致案例數＝0。
  3. 不比舊版差：每組隨機案例，新版晚到站數 ≤ 舊版、步行分鐘 ≤ 舊版、結束時間 ≤ 舊版；步行並列時保留舊版輸出（不無故改順序）。
  4. 不丟站、不隱藏晚到警告；站的內容、換店規則、Google 呼叫次數都不變。
  5. 計算有上限：API 上限 9 站時，單次 `scheduleRoute` 在最壞案例也不卡住請求（測 ≤ 200 ms）；更多站時節點用完就回目前最好的排法（不比貪婪差）。
  6. 新測試修正前失敗、修正後通過；全套單元測試、lint、`npm run typecheck`、CI 綠。舊指紋測試依新規則重算，PR 寫明理由。
  7. 真的 API 跑通：Vercel 預覽站、正式站各真 POST 一次（多站、含固定行程），`routeVerified:true`，回傳的 travelMinutes ≤ 同一步行矩陣下舊貪婪的結果。證據存檔。
  8.（預覽站實測補齊，不改成功指標的意思）不能為了少走路而空等、把店排到更晚：回傳排法的結束時間（最後一站離開）≤ 參考排法的結束時間。參考排法＝舊版結果（貪婪；貪婪報晚到時＝最少晚到排法）。可檢查條件：沒有任何排法「晚到站數更少」，或「晚到相同、步行更短、而且結束不比回傳排法晚」。
     證據：`preview-pinned.json`（第一版只比步行）：先到 22:00 的固定行程空等約 3.5 小時，其餘 8 站排到 22:47–02:04，7 站打烊；總步行 99 分鐘，舊版 112 分鐘。

  - 路線終點是最後一站，不算走回出發點（沿用現有 `visit`）。
